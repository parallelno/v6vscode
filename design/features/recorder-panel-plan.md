# Recorder Panel and Reverse Instruction Stepping — Implementation Plan

**Status:** Implemented across v6emul and v6vscode. The Extension Host smoke test covers panel lifecycle; manual visual checks and performance targets remain unverified.

## 1. Problem

### Current behavior

- v6emul records through `Debugger::Debug` when debugging is attached. `Recorder::Update` receives each instruction's RAM writes and records a checkpoint when `Display::Update::frameNum` changes. A **checkpoint** is a saved emulated state at a particular point in execution. The frame ring is configured for up to 3,000 checkpoints (about one minute at 50 Hz).
- A checkpoint contains CPU state, memory mapping, I/O state, and display timing. The recorder keeps RAM write deltas and a separate full RAM image; it does not store a full copy of all hardware every frame. The frame checkpoint is taken after the instruction that crosses the frame boundary, not at the exact raster boundary. Timer, sound-chip, and floppy-controller state are not in the existing checkpoint.
- IPC commands 53–59 cover clear, frame playback in both directions, separate recorded/current counters, and legacy binary serialization. The two counters are not an atomic timeline status and do not say whether hardware is at a checkpoint or still in a partially executed frame. The extension has no Recorder UI. Trace Log records execution for inspection, not enough state to restore hardware.

### Desired behavior

Open **Recorder** from the `v6emul` Panels launcher. A timeline bar shows the full retained range, the current position, and tick marks for frame checkpoints and recent instruction stops. While paused, users can navigate one recorded frame or instruction at a time in either direction, with up to **1,000 consecutive instruction steps** retained. The debugger and Display must show the restored position without requiring a Continue/Pause cycle.

### Root cause

The existing recorder groups writes by frame and saves only frame-boundary state. It cannot find the exact state before an arbitrary recent instruction. It also uses a combination of ring indices and `m_lastRecord` to represent the partially recorded frame; that representation cannot safely coordinate instruction rewind, frame playback, and resuming execution.

## 2. Strategy

### Approach: one timeline, two retention depths

A **timeline position** identifies an emulation boundary and the corresponding offset in a journal of state changes. The **cursor** is the position currently restored in hardware; the **recorded tip** is the newest retained position. Keep up to 3,000 frame checkpoints and a separate ring covering the newest 1,000 instruction transitions on the same path. Share RAM and other variable-sized changes between the two histories instead of copying bulk memory per instruction. Keep the authoritative timeline on the emulation thread.

| Action or condition | Required behavior |
| --- | --- |
| **Back Instruction** | Restore the state before the most recent completed instruction at the cursor, without executing CPU code. Count interrupt acknowledge plus its injected RST as one step. Count entry into `HLT` once; subsequent halted idle cycles do not consume steps. When halted, stepping back over `HLT` also undoes its trailing idle time; stepping back over an interrupt restores the halted state just before acknowledge. Use explicit CPU boundary signals, not PC changes or `IsInstructionExecuted()` alone. |
| **Back Frame** | Restore the nearest frame checkpoint strictly before the cursor. From mid-frame, this lands at the start of the current recorded frame; from a checkpoint, it lands at the previous checkpoint. A frame checkpoint is the first legal CPU boundary after the display frame number advances, never a mid-instruction snapshot. While halted, an idle machine-cycle boundary can serve as a frame checkpoint without adding an instruction step. |
| **Forward Instruction** | Restore the post-state of the next retained instruction transition from the cursor. Apply its recorded changes; do not execute CPU code or trigger debugger checks. Any recorded idle or input changes before that instruction are included in the restore, but no idle-only step is exposed after the last instruction. |
| **Forward Frame** | Restore the next retained frame checkpoint strictly after the cursor. Do not execute instructions and do not expose a synthetic frame for the partial tail. |
| **Mix frame and instruction navigation** | Recompute both instruction counts from the restored cursor. An old frame before the oldest retained instruction's pre-state has neither instruction action available: Forward Instruction must not skip an unrecorded gap. Frame navigation can re-enter the retained instruction window. An instruction move in either direction may cross a frame checkpoint without dropping frame history. |
| **Continue or step forward after browsing** | Before the first new machine cycle, discard the old future, including only the suffix after the cursor within a partially retained frame. Start recording new execution from restored hardware. Moving the cursor without executing does not discard the future. |
| **State replacement** | Reset, restart, program load, and media replacement establish a new baseline after the full operation, including debugger memory-edit reapplication and before any autorun. There is no Clear History control in the panel. |
| **At an end of history** | A movement with no target succeeds with `moved: false`; hardware, cursor, stop record, and analysis caches are unchanged. Requests based on an obsolete timeline revision are rejected rather than silently moving a replacement timeline. |

Capture starts when the debugger attaches, including launcher-owned Run sessions where the coordinator already attaches debugging. The panel does not enable debugging on its own, and hiding or closing it never changes capture. Detach clears the history so no unrecorded gap can be rewound; a new attach starts at a fresh baseline. Reopening the panel within a session reads current server status; switching connections never reuses cached history or pending actions.

### Why this works

Saving compact hardware state at legal instruction boundaries makes one reverse step a restore, not a replay of code, Lua callbacks, or host input. The same ordered change journal lets frame playback move across many instructions and lets instruction rewind cross a frame boundary without invalidating either history. Keep user-facing **machine state** (registers, RAM, emulated peripheral state and timing) separate from **debugger state** (breakpoint definitions, trace queries and statistics) and **host state** (files, sound already emitted, and physical keys currently held).

### Summary of changes

1. Replace ambiguous recorder indexing, add bounded instruction capture, and make restoration coherent across hardware subsystems.
2. Advertise a versioned Recorder IPC contract alongside protocol v2; do not infer support from the legacy IDs.
3. Add a standalone editor panel using the existing panel infrastructure and route movement through the active session's execution owner.
4. Verify exact restore, timeline branching, runtime budgets, and VS Code refresh against a real emulator before release.

## 3. Implementation Steps

### Step 3.1 — Characterize the existing recorder and define the state boundary [ ]

- Add small C++ fixtures for ring wrap, the first reverse from mid-frame, repeated writes to a single address, exact frame landing, and forward playback after reverse. Record known failures before replacing the indexing, including the wrapped decrement at slot zero and the legacy distinction between the live tail and newest checkpoint. Verify whether `GetFrame(true)` returns the rebuilt frame or a stale back buffer.
- Audit `Hardware::ExecuteInstruction`, the CPU's `HLT`/interrupt behavior, exception cleanup, and the alternate `RunHeadless` loop. Expose explicit instruction retirement and idle/interrupt boundaries. Capture the pre-state before any relevant machine cycle and commit the transition after final debugger write corrections and hardware exception cleanup, before polling the request queue. Do not add history for debugger-only or host-only operations to the instruction count. Cover normal run, instruction stepping and both frame-step commands using the common execution path; the CLI headless path remains unrecorded and an IPC headless run, if allowed while attached, starts a new baseline rather than leaving a gap.
- Inventory mutable state beyond the existing recorder: timer counters and AY chip phase/registers, audio state that affects future emulation, FDC registers/transfer cursor, mounted image contents and dirty flags, keyboard matrix, memory mapping, I/O latches, IRQ/raster state. Define explicit value snapshots; reconstruct references (for example, FDC drive/byte offset) on restore instead of saving raw pointers, callbacks, mutexes, or C++ object representations. For RAM, verify whether the CPU debug slots cover every committed write; journal at the mutation path where necessary. Undo writes in reverse order and redo in original order using physical addresses, including mapped RAM disks and corrected read-only writes.
- Classify non-instruction changes instead of silently ignoring them. Journal runtime keyboard events at safe boundaries without counting them as instructions; reconcile physical held keys as a new input at the first resumed execution, without modifying the browsed state. Treat direct RAM/palette edits, changes to emulated hardware configuration, disk mount/dismount and disk-save acknowledgement as baseline changes; centralize this at the mutation boundary and preserve the current recorder on rejected/no-op requests. Audit all other hardware mutation paths, including `DEBUG_RESET` when it requests a recorder reset. A future script API that writes hardware must use the journal or establish a baseline.

> **Implementation Notes:** Core IPC tests cover frame landing, a floppy write/transfer, and halted idle. Hardware now owns capture and restores full RAM-disk mapping and peripheral state.

### Step 3.2 — Implement the bounded timeline and restore path in v6emul [x]

- Keep a compact before/after state at instruction boundaries (adjacent states may share storage) with journal offsets and an instruction ordinal. Keep frame checkpoints with the same position coordinates. Record the live partial tail separately from frame checkpoints. The journal holds ordered old/new RAM and in-memory disk bytes and any other variable changes; restore it without calling emulated write handlers, scripts, or watchpoints. Group or compact idle records; retain frame and interrupt boundaries while halted. Both rings must pin the journal ranges they need. Use explicit bounds and wrap-safe indexing; never manufacture an instruction step when a required record was evicted.
- Frame movement seeks through the journal, then installs the target hardware snapshot. Instruction movement seeks to the previous instruction's pre-state or the next instruction's post-state, then installs that snapshot. Assign increasing position IDs to recorded boundaries, sharing an ID when a checkpoint and an instruction stop represent the same state. A backward target uses the last retained instruction whose post-state is at or before the cursor; a forward target uses the first retained instruction whose pre-state is at or after the cursor, subject to the no-gap rule above. Establish a new branch before the first new machine cycle, including when stepping after a rewind; synchronize the frame-number latch and truncate only the future. Keep frame and instruction budgets independent: an old or unusually write-heavy frame must not evict required instruction history. Reserve enough storage for the worst-case changes from 1,000 supported instruction transitions, with bounded compaction for events between them. If the frame journal reaches a byte budget, evict oldest complete frame intervals first and report actual retained depth. Allocate fixed instruction storage once and avoid allocations or full RAM/framebuffer copies on the instruction hot path.
- Restore keyboard, timer, AY, FDC transfer state and in-memory image changes alongside CPU, RAM, I/O, and raster timing. Restore disk dirty state consistently with the current saved image generation; never save, load, or replace a host file as part of navigation. Flush queued host audio without resetting the restored emulated chip state. Rebuild and publish the Display preview once per successful movement through the existing frame path, without modifying the restored raster state; preview is reconstructed from restored video state, not promised pixel-identical to the historical scanout. Verify paused and resumed display-buffer behavior separately.
- On a successful movement, invalidate Trace Log filters, function history, active call tracking, watchpoint partial matches and memory-access highlights, and cancel in-progress performance samples. Preserve debugger definitions, breakpoint counters, completed statistics, and Lua globals. Do not rerun or rewind Lua. Keep emulated cycles/frame coordinates separate from monotonic session statistics: accumulate actual executed work without counting reverse or frame playback as new work. Preserve `lastRunCycles` on navigation; avoid unsigned underflow after rewinding an attached session.
- Test reference snapshots at every boundary, then reverse, browse forward again, and separately resume with the same inputs to compare emulated state. Compare before/after for RAM, mapping, CPU internals, IRQ/EI/HLT, timer/AY, keyboard and FDC, not only PC. Prove 1,000 reversals after executing more than 1,000 instructions, followed by 1,000 forward restores without executing code. Verify a no-op at both limits, idle/input gaps, a rewind across frames, frame/instruction alternation, saturated rings, same-address writes, and divergence after resuming. Restore a dirty disk sector both ways and verify that no host file changes.

> **Implementation Notes:** Uses a fixed-capacity instruction ring, a bounded frame ring, and a shared byte journal. The emulator test executes 1,030 instructions, compares 1,000 exact register/RAM restores each way, then verifies that new execution drops the old future.

### Step 3.3 — Publish Recorder schema 1 in emulator IPC [x]

Proposed IDs follow the current last public command (113); confirm allocation in both repositories before implementation. Keep transport and protocol version unchanged. Advertise `recorderSchema: 1` and `recorderLimits: { maxFrameCheckpoints, maxInstructionSteps }` from `GET_SERVER_INFO`. Require the schema, valid limits, both command IDs, and the existing stop-record contract in the extension. Do not make ordinary Run or Debug depend on Recorder support.

| Proposed command | Request `data` | Success `data` |
| --- | --- | --- |
| 114 `DEBUG_RECORDER_STATUS` | Omitted or `{}` | `RecorderStatus` |
| 115 `DEBUG_RECORDER_MOVE` | `{ action: 'backFrame' \| 'backInstruction' \| 'forwardInstruction' \| 'forwardFrame', expectedRevision: number }` | `{ moved: boolean, status: RecorderStatus, stopSequence?: number }` |

`RecorderStatus` is one atomic snapshot: `attached` and `running` Booleans; `revision` (non-negative safe integer scoped to the connection's emulator process); `frameCheckpoints`, `frameStepsBack`, `frameStepsForward`, `instructionStepsBack`, and `instructionStepsForward` (non-negative bounded counts); and `position`, either `null` when detached or `{ id, pc, frameNumber, atFrameCheckpoint, atRecordedTip }`. `frameNumber` is the rewound display coordinate, not a monotonic statistic. Navigation counts describe valid targets from the cursor, not ring slots. Advance `revision` on invalidating state changes (capture, move, baseline replacement, branch, run/stop and attach/detach), including paused state changes that can make a rendered control stale. No-op moves do not advance it.

Include `timeline: { oldest, newest, instructionStart, frameTicks, instructionTicks }` when attached and `timeline: null` when detached. Positions and ticks are non-negative safe integer IDs; `oldest <= position.id <= newest`. `instructionStart` is the oldest retained instruction pre-state or `null` when none exist. Each tick array is sorted, unique within its kind, and within the retained range. The frame array represents frame checkpoints; the instruction array represents the union of retained pre- and post-states, deduplicated by position. Return every tick for a kind with up to 40 stops; otherwise return the first, every tenth thereafter, and the last if not already included. Bounds are 301 frame ticks and 201 instruction ticks at maximum capacity. Compute this metadata from indexes, not by scanning the write journal; cache samples until their stop lists change. Samples describe the ruler only and never determine which actions are available.

- Add IDs to the public request enum, supported command checks/listing, and request validation in the app layer. Keep capture, paused/attached checks, revision comparison and mutation on the emulation thread, in one request. Status is readable while running; movement requires stopped, attached hardware. Reject unknown fields, invalid enums and unsafe revisions with `invalid_request`. Use `dispatch_error` with stable `details.reason` values (`running`, `not_attached`, `stale_revision`) for failed state preconditions. No failures may leave partially restored state. Test malformed inputs and stopped/running races using IPC and direct core calls.
- On movement only, record exactly one stop at the restored PC and mapped address with existing reason `step` for instruction movement or `frameStep` for frame movement, plus a Recorder-specific description. Return the new stop sequence only when `moved` is true. Keep the emulator stopped; do not call `STOP` just to update the record. Reuse the existing stop decoder and leave old clients' reason handling intact.
- The panel does not use commands 53–59. Keep the existing frame-only command IDs and response shapes, routing navigation and clear through the same guards, consistency hooks, and canonical cursor. Legacy blob import/export is out of scope for the panel; do not write new in-memory structs into the v1 format. Where legacy representation is still supported, validate input fully before mutation and reset/reseed the instruction window on a successful import; reject states or imports that cannot be represented/restored safely with a structured error rather than partially restoring them. Document the compatibility limits and test that legacy calls cannot leave a stale instruction future. Do not advertise the new schema until these interactions are safe.

> **Implementation Notes:** IDs 114 and 115 are implemented and exercised by live IPC conformance. Legacy blob commands reject with `legacy_blob_unsupported`; frame-only navigation and reset use the new timeline.

### Step 3.4 — Add Recorder panel and execution-owner integration in v6vscode [x]

Illustrative layout (the diamond marks the restored position):

```text
Oldest                                              Newest
|=============◆------------------------------------------|
|     |     |     |     |     |     |      |||||||||||||||
[Back Frame] [Back Instruction] [Forward Instruction] [Forward Frame]
```

- Add `v6emul.toggleRecorder`, the `v6emul.recorderOpen` context key and a **Recorder** launcher entry next to Trace Log. Use editor `WebviewPanel` ID `v6.recorder`, title **Recorder**, and `v6.refreshRecorder` in the editor title. Wire `package.json`, contribution IDs, the launcher, and `extension.ts`. Compose `PanelHost` with one panel instance, existing webview assets/build configuration, content security policy, and typed, runtime-validated host/webview messages. The webview does not send arbitrary IPC commands.
- Place the timeline bar above the buttons, with oldest history at the left and newest at the right. Fill to the current position and draw a separate cursor marker. Use taller frame ticks and shorter instruction ticks on or under the bar, with a legend; do not rely on color alone. If the dense instruction range would become unreadable on a linear scale, give it the rightmost third of the bar and map the older frame range to the remainder; mark the scale break. With no older range or no instruction range, use the full width for the available range. Coalesce same-kind ticks that render within 3 CSS pixels while preserving endpoints and the current-position marker. Display counts separately so sampling never implies missing stops. The bar is read-only in v1: ticks show where stops are, and only the buttons navigate.
- Use this button order: **Back Frame**, **Back Instruction**, **Forward Instruction**, **Forward Frame**. Display the cursor frame and PC and the exact number of available steps in each direction. Support keyboard navigation and accessible labels; show readable states for disconnected, unsupported, detached, running, paused/empty, busy, and error. Do not queue clicks while busy or silently pause the emulator to fulfill a click. Disable each movement with no target; explain that older frame checkpoints may have no instruction history.
- Add a Recorder service with schema-gated typed commands and runtime response validation in the emulator protocol layer. Capture a `SessionCoordinator` lease before awaiting, check after every await, and bind UI actions/results to the active panel token, connection, and revision. Start with status on ready/reveal, state or position change, successful operations, and manual refresh. If showing live counts, issue only a coalesced low-priority status poll while visible and running (at most twice per second). Stop polling on hide/dispose/disconnect. On stale revision refresh without replaying the click; do not auto-retry a timed-out mutation whose outcome is unknown.
- For Debug Adapter Protocol (DAP) sessions, route movement via `ExecutionController` and its active `V6DebugAdapter`, not by sending execution IPC from the webview. Serialize with continue, pause, step, source-step, reset and disconnect transitions; a shared socket queue by itself does not serialize multi-request actions. Do not let an in-flight source step or temporary breakpoint survive into a restore. Consume the returned stop sequence exactly once and use the existing paused refresh path to invalidate registers, stack/scope/variable handles, disassembly and source location. Emit one stopped event (reason `step`) for a successful move and no synthetic continued event. Make the timeline replacement explicit so it cannot be interpreted as progress of a source step or a logpoint. No-op movement does not emit a stopped event.
- In a launcher-owned Run session, perform eligible paused operations through the coordinator and publish the same session-scoped position-change notification without DAP events. In both modes, refresh visible Display, Hardware Statistics, Ports, Hex Viewer, Memory Edits and Trace Log after a move even when the running flag has not changed. Reuse the existing frame request path with an explicit paused refresh signal and reject stale in-flight view reads. Opening Recorder must never create a new emulator connection or change attach/run state.

> **Implementation Notes:** Recorder uses `PanelHost`, a revision-scoped service, a canvas ruler, the four paused controls, and the DAP execution controller. Visible paused status refreshes once per second as well as on lifecycle events to pick up external changes without retrying mutations.

## 4. Expected Results

- At a breakpoint just after a wrong RAM write, **Back Instruction** restores the previous byte and the instruction's pre-execution PC. **Forward Instruction** restores the recorded write and post-state without executing the instruction. At either end of the retained instruction window, the corresponding button is disabled rather than falling back to a frame jump.
- When a rendering bug spans many frames, **Back Frame** goes to the nearest earlier checkpoint, **Forward Frame** browses checkpoints without running code, and **Continue** from a checkpoint discards only the abandoned future. Display and debugger views update at each successful move while the emulator stays paused.

## 5. Risks and Mitigations

| Risk | Mitigation |
| --- | --- |
| Correct PC but incorrect execution after resume | Validate the full restore state and deterministic forward execution, including interrupt, peripheral, memory mapping and host-input boundaries. |
| 1,000 records are too expensive or evicted by a write-heavy frame | Use compact snapshots and bounded, shared deltas; reserve the instruction window independently, profile release builds and report frame evictions. |
| Preview draws future pixels or changes raster state | Publish the rebuilt paused image through the actual frame-serving path, preserve emulated timing, and test both paused and first resumed frames. |
| Restore collides with execution, debugger stop polling, or reconnect | Use emulation-thread guards, revision checks, execution-owner sequencing, session leases, and stop-sequence deduplication. |
| Lua or host file effects cannot be undone | Restore emulated state only. Do not rewind Lua globals, external files, or audio already played; document the distinction and clear history at external state replacement boundaries. |

## 6. Relationship to Other Improvements

Reuse the Panels launcher, `PanelHost`, stop-record handling, and Trace Log invalidation. Recorder does not use Trace Log as a restore source, and it must not preserve active calls or trace rows from an abandoned future. Emulator owns state, IPC owns the boundary, the execution owner coordinates movement, and the panel renders status and sends user intent.

## 7. Future Enhancements

Native DAP `stepBack` and reverse-continue, a draggable timeline scrubber, configurable history depths, and a portable versioned import/export format. These are not required for the first release; do not advertise native reverse-debug capabilities until the corresponding DAP behavior is implemented and tested.
